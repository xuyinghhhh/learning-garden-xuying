## 一、总览：今天做成了什么

今天，我和 AI 助手一起搭建了一个属于自己的个人学习网站。它既是个人主页，也是可以持续更新的学习笔记空间。别人打开网址就能阅读；我可以通过网页编辑器登录 GitHub，写笔记、修改内容并发布。

这次最重要的成果，是走通了一次完整流程：**提出想法 → 制作网页 → 上传 GitHub → 网站上线 → 配置编辑器登录 → 写第一篇笔记 → 修复部署问题 → 在公开网站读到新笔记。**

本文中的“我”指网站所有者，“助手”指协助搭建的 AI。截图来自本次实际操作，不是教程示意图。涉及账号登录的过程只记录方法，不记录密码、Client Secret 或令牌；部分账户配置截图因此没有收录。本文反映的是 2026 年 10 月 23 日这次搭建过程，平台界面以后可能变化。

## 二、分步回顾：网站是怎样搭起来的

### 第 1 步：把“我想要一个页面”说清楚

我的最初想法是：有一个能放进 GitHub 个人主页的链接，点进去能看个人介绍、开发项目链接、最近学习的内容，以及我和助手沟通后整理的记录。

随后又补充了几个关键要求：

- 我自己能在网页里写笔记，也希望助手能帮忙维护。
- 阅读者不用登录 GitHub，直接访问网站即可。
- 笔记按日期和主题整理，支持搜索。
- 不只有文字，后面还要放图片和表格。

助手据此将网站分成“公开阅读页面”和“需要登录的编辑器”。这一步很重要：**读者不登录，不等于任何人都可以修改网站。**

### 第 2 步：决定把内容存到 GitHub

我接受了“GitHub 保存 Markdown”的方案。这里的意思是：每篇笔记是一份文字文件，放在仓库的 `content/notes` 文件夹里；图片作为单独的文件放在 `public/uploads` 中；Markdown 通过图片地址把它引用进来。

Markdown 可以表达标题、列表、链接、引用、代码和普通表格。例如：

```markdown
## 今天学到的内容

- 学会进入网站编辑器
- 学会填写标题、日期和主题

| 内容 | 收获 |
| --- | --- |
| GitHub | 保存笔记和修改历史 |
| Markdown | 用文本组织内容 |
```

因此，选择 Markdown 并不意味着以后只能写纯文字。只是图片本身不塞进 Markdown 文本，而是由文本引用图片文件。

### 第 3 步：在 D 盘准备网站

我明确要求所有尝试放到 D 盘的新文件夹，助手使用了 `D:\个人学习网站`。

助手制作了公开页面、搜索与筛选功能、笔记阅读页面，以及将 Markdown 转成网站内容的构建脚本；准备了两篇初始内容：《从这里开始，记录每天的学习》和《图文与表格，笔记可以这样写》。后一篇是格式示例，不代表我的真实学习经历。

主要文件的作用如下：

| 文件或目录 | 可以把它理解成什么 |
| --- | --- |
| `public/index.html` | 网页的结构 |
| `public/style.css` | 网页的颜色、排版和外观 |
| `public/app.js` | 搜索、筛选、打开笔记等交互 |
| `content/notes/*.md` | 一篇篇学习笔记的原稿 |
| `public/uploads` | 文章用到的图片 |
| `build.mjs` | 把原稿整理成网站可读取内容的程序 |
| `tests.mjs` | 检查表格、图片、内容处理和草稿过滤等行为 |
| `dist` | 本地构建后得到的网站成品 |
| `.github/workflows/pages.yml` | 告诉 GitHub 如何自动构建和发布 |

网站构建时生成 `notes.json`，公开页面再读取它来展示文章。以后笔记更新，自动部署会重新生成这一份内容。

### 第 4 步：登录 GitHub，使用项目仓库

我登录了 GitHub，并提供了自己的主页地址。最终使用的账号是 `xuyinghhhh`，仓库名称是 `learning-garden-xuying`。

“仓库”可以理解为一个带修改历史的项目文件夹。它存放的不只是网页，也包括笔记和图片。

![GitHub 仓库中的网站目录和文件](/learning-garden-xuying/uploads/2026-10-23-build-log/01-repository.png)

*图 1：实际仓库页面。这里已经能看到笔记目录、网页目录和构建脚本。截图记录的是中途状态，不是最终文章数量。*

### 第 5 步：跳过 GitHub 插件，继续完成工作

过程中尝试连接 Codex 的 GitHub 插件，出现了 ChatGPT 登录与双重身份验证页面。我发现自己的 GitHub 邮箱和 Codex 邮箱不是同一个，也对手机号验证产生了疑问。

随后我明确决定：先跳过插件，等以后再安装；如果助手不能在 GitHub 上直接操作，就指导我操作。

于是后面的协作方式变成了：**助手准备文件和步骤，我完成账号内的操作并发送截图，助手根据截图和公开网站结果继续检查。** 网站没有因为插件没装好而停下来。

这里需要区分三个账号：GitHub 用来保存和修改仓库；Cloudflare 用来运行登录服务；ChatGPT/Codex 用来与助手协作。它们不要求使用同一个邮箱。这次网站编辑器最终走的是 GitHub 登录流程。

### 第 6 步：上传文件，配置 GitHub Pages

助手准备了可以上传的项目文件。我通过 GitHub 网页上传，并按指导补上自动发布工作流、配置 GitHub Pages。

上传文件和发布网站是两回事：仓库有代码，只表示文件已经存上去；发布工作流还要运行构建、生成网站成品，再把成品交给 Pages 托管。

这次使用的流程是：

```text
文件提交到 main 分支
        ↓
GitHub Actions 运行测试
        ↓
构建网页与 notes.json
        ↓
GitHub Pages 发布
        ↓
访客通过网址阅读
```

助手检查了发布结果和公开页面，确认网站已经能够访问。到这里，“别人能打开网站阅读”已经实现，但“我能在网页里写笔记”还需要下一阶段。

### 第 7 步：选择 Cloudflare 承担编辑器登录服务

为了支持网页写笔记，助手配置了 Decap CMS 编辑器。它提供标题、日期、主题、正文等编辑界面，但还需要一个服务来完成 GitHub 登录授权。

我注册了 Cloudflare 账号。这里 Cloudflare 的职责是运行一个小型登录程序；公开网站本身仍然托管在 GitHub Pages。

可以这样理解各部分分工：

| 部件 | 在这次网站里的职责 |
| --- | --- |
| GitHub Pages | 把公开网站提供给读者 |
| GitHub 仓库 | 保存 Markdown、图片和网页代码 |
| Decap CMS | 提供我写笔记的网页界面 |
| Cloudflare Worker | 协助编辑器完成 GitHub 登录授权 |
| GitHub OAuth App | 让 GitHub 识别这个编辑器，并向我请求授权 |

### 第 8 步：创建 Cloudflare Worker

我在 Cloudflare 控制台依次进入创建应用页面，选择 `Start with Hello World!`，创建名为 `learning-garden-auth` 的 Worker，并点击部署。

最初的 `Hello World!` 只是一个默认示例，用来建立服务入口。它还不具备真正的编辑器登录功能，后面需要替换成助手写好的程序。

随后进入 Worker 的设置，找到 `Runtime variables and secrets`。截图中的 `Add variable` 是添加配置的入口；下面的 `Add binding` 是另一种功能，不是这次填写客户端配置的位置。

![Cloudflare Worker 的变量与密钥设置区域](/learning-garden-xuying/uploads/2026-10-23-build-log/03-worker-settings.png)

*图 2：设置区域。填写配置时使用上方 Add variable，选择 Production 环境。*

### 第 9 步：在 GitHub 创建 OAuth 应用

我在 GitHub 的开发者设置中创建了名为 `Learning Garden Editor` 的 OAuth 应用，填写了应用主页和登录回调地址。

“回调地址”就是 GitHub 完成授权后，将浏览器送回登录服务的地址。本次它指向 Cloudflare Worker 的 `/callback` 路径，而不是公开网站首页。它必须与登录程序使用的地址一致。

![GitHub 显示 Learning Garden Editor 创建成功](/learning-garden-xuying/uploads/2026-10-23-build-log/02-oauth-created.png)

*图 3：Application created successfully 表示 OAuth 应用已经建立，但此时还没有完成整个登录链路。*

这一步生成的两个配置用途不同：

| 配置 | 用途 | 本次如何保存 |
| --- | --- | --- |
| `GITHUB_CLIENT_ID` | 标识是哪一个 OAuth 应用 | Cloudflare 普通变量 |
| `GITHUB_CLIENT_SECRET` | 登录服务与 GitHub 交换授权结果时使用的秘密 | Cloudflare Secret，启用加密保存 |

我把它们填入 Worker 的 Production 配置。Secret 不应放进公开仓库、Markdown 或前端页面。本文也不展示它的值。

### 第 10 步：部署真正的登录程序

助手编写了 Worker 登录程序，我通过 `Edit code` 将它放入 Cloudflare，并部署。

程序的主要工作是：引导我去 GitHub 授权，接收返回结果，检查登录过程是否有效，并确认账号是网站所有者，再将登录结果交给编辑器。它还使用了防止授权请求被冒用的校验机制，包括 state 和 PKCE；日常使用时不需要手动处理这些内容。

助手分别检查服务首页和登录入口：服务首页返回了登录服务说明，登录入口会跳转到 GitHub。**这只能证明入口能工作，还不能代替真实登录测试。**

### 第 11 步：配置并上传网页编辑器

助手准备了 `public/admin/index.html` 和 `public/admin/config.yml`，我将它们上传到仓库，等待网站再次部署。

编辑器配置指定了仓库、main 分支、Cloudflare 登录服务、笔记目录和图片目录，也定义了这些字段：标题、日期、主题、类型、简介、草稿、正文。

完成后，网站多了一个入口：在网站网址后加上 `/admin/`，就可以打开笔记编辑器。

### 第 12 步：审核 GitHub 授权并登录

我在编辑器中点击 GitHub 登录，出现授权弹窗。弹窗里的应用是自己创建的 `Learning Garden Editor`，账号也是自己的 GitHub 账号。

*图 4：登录时的实际授权页面。点击绿色授权按钮前，需要查看应用名称、账号和权限范围。*

我审核后点击授权，随后成功进入编辑器，并看到了原来的两篇笔记。

### 第 13 步：填写第一篇真实笔记

我点击“＋ 学习笔记”，按助手提供的示例填写《我的个人学习网站上线了》：主题为“个人网站搭建”，类型为“学习笔记”，简介和正文记录当天的建站成果。

![第一篇笔记的填写界面，日期未填且草稿开启](/learning-garden-xuying/uploads/2026-10-23-build-log/06-writing.png)

*图 6：当时标题和正文已经写好，但日期仍为空，草稿开关仍为蓝色。这张图保留了发布前需要检查的真实状态。*

助手根据截图指出还差两项：点击日期栏里的“现在”填写日期；关闭“草稿”开关，让它变灰，然后再发布。

### 第 14 步：点击发布，笔记保存到仓库

我补上日期、关闭草稿并点击发布。页面显示“修改已保存”和“已发布”，说明编辑器已经完成保存。

### 第 15 步：发现网站部署失败

助手没有只凭“已发布”三个字就认定全部完成，而是读取公开网站的 `notes.json`，发现仍然只有两篇旧笔记；再检查 GitHub Actions，发现最新一次运行失败，停在测试步骤，后续构建和部署没有执行。

接着检查仓库，确认我的新笔记确实已经保存。由此可以把问题范围缩小到：**内容已经写入，但网站处理这份内容时失败。**

### 第 16 步：找到 Markdown 元数据格式差异

每篇笔记开头都有一段元数据，用来保存标题、日期、主题和草稿状态；正文在元数据之后。

原来的构建程序接受这样的格式：

```text
---
{"title":"示例","date":"2026-10-23","draft":false}
---
这里是正文。
```

编辑器实际保存的格式却是：

```text
---
"title": "示例",
"date": "2026-10-23",
"draft": false
---
这里是正文。
```

区别在于最外面的一对大括号。原程序直接把这一段交给 JSON 解析，因此第二种格式会报错。这是程序兼容性问题，不是我填写错了，也不需要重新写笔记。

### 第 17 步：先复现，再修复，再验证

助手补充了一条测试，专门输入编辑器实际生成的格式，先确认旧程序会报错；随后修改解析逻辑：已有大括号的格式照常解析，省略大括号的格式则补齐后解析。

修复后再次运行测试，并使用仓库中真实的新笔记做构建验证。结果从“构建出 2 篇公开笔记”变成“构建出 3 篇公开笔记”，同时保留对图片、表格、危险链接、HTML 处理和草稿过滤的检查。

## 三、以后怎么使用：把今天的步骤变成习惯

### 日常发布一篇笔记

**准备：** 只需要浏览器、网络和自己的 GitHub 账号。平台已经搭好后，不需要每天上传代码，不需要每天打开 Cloudflare，也不需要每次重新创建 OAuth 应用。

1. 打开在线编辑器，使用自己的 GitHub 账号登录。
2. 点击“＋ 学习笔记”，或打开已有文章进行修改。
3. 填写标题、日期、主题、类型、简介和正文。
4. 检查右侧预览，确认文字和图片内容适合公开。
5. 想在网站展示，就关闭草稿开关，然后发布。
6. 等待 GitHub Actions 部署完成，再打开公开主页检查。
7. 如果浏览器还显示旧内容，可以用 Ctrl＋F5 刷新；若仍没变化，检查部署结果。

### 实际演练：明天我想写一篇学习笔记

**第一步，在浏览器打开 [在线编辑器](https://xuyinghhhh.github.io/learning-garden-xuying/admin/)。** 如果已经登录，会直接看到笔记列表；如果显示登录按钮，就使用自己的 GitHub 账号完成登录。已有登录授权不代表会话永远有效，过期后重新登录即可。

**第二步，点击“＋ 学习笔记”，填写以下内容。** 表中的文字只是明天可以参考的填写示例，不会自动生成一篇文章。

| 字段 | 示例 | 用途与注意点 |
| --- | --- | --- |
| 标题 | 今天学会了用 Markdown 写表格 | 告诉自己和读者这篇文章讲什么 |
| 日期 | 选择实际记录日期 | 用于日期展示和月份筛选；别留空 |
| 主题 | Markdown 学习 | 尽量复用统一名称，避免同类内容被分散 |
| 类型 | 学习笔记 | 沟通回顾可以选“沟通整理” |
| 简介 | 用一个小表格整理知识点和下一步练习。 | 用一两句话说明文章内容 |
| 草稿 | 准备公开时关闭 | 关闭后才会被构建程序纳入公开网站 |
| 正文 | 问题、学到的内容、例子、下一步 | 可以使用标题、列表、图片和 Markdown 表格 |

**第三步，检查预览并点击“发布”。** 看见“修改已保存”说明内容已经写回 GitHub。此刻不要把“编辑器保存成功”误认为“主页已立即更新”。不用再手工复制同一篇文章到仓库，否则可能产生重复文件。

**第四步，等待自动部署，打开 [Actions](https://github.com/xuyinghhhh/learning-garden-xuying/actions) 查看最新运行。** 队列或运行中表示尚未完成；成功表示本次发布流程完成；失败则点开运行详情看失败步骤。等待多久取决于当时的运行情况，不保证固定秒数。

**第五步，打开 [公开主页](https://xuyinghhhh.github.io/learning-garden-xuying/)，搜索刚才的标题。** 点击文章，检查日期、正文和图片。确认能读到以后，再复制浏览器里的文章地址分享给别人；文章地址通常是在网站地址后带有 `#note/…`。

### 已经发布的笔记，怎么修改和同步

进入编辑器 → 点击已有笔记标题 → 修改正文或其他字段 → 发布 → 等待 Actions 成功 → 刷新文章页面。只要仓库连接和部署配置正常，后续修改也会沿着同一条链路自动更新。

如果只是把文本输入框改了，却没有发布，公开网站不会自动跟着变化。如果把草稿打开后保存，下一次成功构建会将这篇文章从网站展示中排除；但这不是对公开仓库内容的隐私保护，也不会自动抹掉仓库历史。

### 如果让助手帮我整理笔记，我该怎么说

可以给出明确请求：“把今天关于某个主题的讨论，整理成一篇学习笔记，包含结论、例子、图片和下一步，先给我预览。”确认后再说“发布到学习网站”。

助手整理好的文章仍然需要进入同一个 GitHub 仓库，才会触发网站更新。若有可用的授权操作方式，可以协助提交；若没有，就准备 Markdown 和图片，由我上传。**只在聊天里生成文档，或只保存在 D 盘，都不会自动变成网站上的公开文章。**



### 图片、表格和沟通记录怎么保存

图片放在网站图片目录，通过编辑器媒体功能或正文中的图片引用加入文章；普通表格可以使用 Markdown 表格语法。当天已经验证网站能展示示例图片与表格，但“通过编辑器上传一张新图片再发布”的完整操作还没有单独验收，不能与文字发布的验证混为一谈。

沟通记录适合整理成“问题是什么、讨论过哪些方案、最后怎样决定、实际结果是什么”的文章，不必把聊天逐字复制。这样回看时更容易理解，也能避免把登录信息、私人内容或无关片段一起公开。

### 几个以后容易忘记的区别

| 容易混淆的事情 | 正确理解 |
| --- | --- |
| 草稿不公开 | 只是网站不展示；仓库本身公开时，草稿原文件仍可能被别人读取 |
| 编辑器显示已发布 | 表示内容保存成功；网站还需要完成构建和部署 |
| 登录 Cloudflare | 是管理登录服务；日常写笔记不需要每次去 Cloudflare 控制台 |
| 用 GitHub 保存笔记 | 访客依然可以直接访问公开网站，不需要 GitHub 账号 |
| 助手帮我发布 | 仍需有可用的登录会话或仓库操作权限；权限不可用时，可以由我上传助手准备的文件 |
| 网站内容有更新，电脑本地也一定有 | 网页编辑器修改的是远端仓库，本地副本需要同步，不能把旧文件整包覆盖回去 |

### 网站没更新时，按这个顺序排查

先看编辑器是否显示保存成功，再看 GitHub 仓库里有没有新文件或新提交，然后看 Actions 最近一次运行是否成功，最后检查公开网站和浏览器缓存。不要一看到旧页面就重复写文章或重复创建账号。
